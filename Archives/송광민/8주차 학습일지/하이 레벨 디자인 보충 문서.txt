======================================================================
0. 이 문서의 목적과 읽는 방법
======================================================================

이 문서는 팀원이 기존 하이레벨 설계를 이해하고, 실제 구현에 필요한
로우레벨 설계 회의를 진행하기 위한 인계 자료다. 완성된 구현 명세서는 아니다.

하이레벨 설계(HLD)는 누가 무엇을 담당하고 누구와 통신하는지 정한다.
로우레벨 설계(LLD)는 이를 구현할 모듈, 함수, 메시지 필드, 자료형,
처리 순서, 오류 처리까지 구체화한다.

예를 들어 '호스트가 발사 요청을 검증한다'는 HLD에 해당한다.
LLD에서는 발사 메시지에 어떤 필드를 넣는지, 어느 스레드에서 검사하는지,
중복 요청을 어떻게 식별하는지, 탄약 차감과 포탄 생성 순서를 정해야 한다.

표시 기준
  [확정] 사용자가 선택했거나 원본 지침에서 요구한 사항
  [기본안] 현재 HLD에서 제안한 방식. 회의에서 채택 여부와 세부 내용을 확정
  [미정] 필요한 정보가 부족하여 추가 결정이 필요한 사항

회의 결과물
  1) 메시지별 패킷 명세
  2) 모듈 및 함수의 책임과 인터페이스
  3) 접속·방·플레이어 상태 전이표
  4) 실패 및 복구 처리표
  5) 담당자, 구현 순서, 검증 시나리오

======================================================================
1. 현재 확정된 범위와 아직 결정하지 않은 범위
======================================================================

[확정]
  - 플레이어 중 한 명이 호스트가 되어 게임 연산을 수행한다.
  - 최대 플레이어 수는 호스트를 포함한 총 3명이다.
  - 별도의 전용 게임 서버는 사용하지 않는다.
  - Photon을 사용하지 않고 소켓으로 직접 구현한다.
  - 별도의 세션 서버가 방 목록과 입장 요청을 관리한다.
  - 호스트와 세션 서버, 게스트와 세션 서버는 TCP로 통신한다.
  - 호스트가 실제 입장을 승인하거나 거절한다.
  - 게스트는 승인 응답 전체를 받은 뒤 세션 TCP를 종료한다.
  - 그다음 새 소켓으로 호스트에 게임 연결을 시도한다.
  - 세션 입장 승인과 실제 게임 참가 성공은 서로 다른 상태다.

[기본안]
  - 게임 TCP: 인증, 초기 상태, 발사·장전 등 요청, 중요 상태 변경.
  - 게임 UDP: 주행·조준 입력, 머리·손 자세, 주기적인 상태 스냅샷.
  - 호스트가 이동·무장·충돌·피해·역할·경기 상태를 최종 결정한다.
  - 입장 승인 시 자리를 예약하고, 게임 인증 후 참가 슬롯으로 바꾼다.
  - 방 상태는 전체 메타데이터와 상태 버전을 함께 보고한다.
  - 첫 버전은 자동 호스트 변경 없이 호스트 종료 시 경기를 종료한다.
  - 진행 중 신규 참가보다 기존 참가자의 재접속을 우선 지원한다.
  - 개발 초기에는 같은 LAN에서 직접 연결을 검증한다.

[미정]
  - 3명이 한 탱크에 탑승하는지와 실제 역할·허용 행동.
    현재 예시는 한 탱크를 공동 조작하는 상황을 가정한다.
  - 게임 TCP/UDP 분담의 최종 채택, 포트, 접속·보안 방식.
  - 세션 서버와 게임 클라이언트의 구현 언어·실행 환경.
  - 인터넷 접속, NAT 대응, 포트 개방 또는 중계 필요 여부.
  - 탱크 물리·포탄 방식, 지연 보정과 예측 범위, 음성 채팅.
  - 갱신 주기, 타임아웃, 재시도 횟수와 상태 보관 기간.

주의: 전용 게임 서버를 사용하지 않는다는 결정과 세션 서버의 존재는
모순되지 않는다. 세션 서버는 게임 세계를 연산하는 서버가 아니다.

2. 구성 요소와 소켓의 관계
======================================================================

전체 연결

  호스트 -------- 세션 TCP 유지 -------- 세션 서버
  게스트 1 ------ 목록·입장 TCP -------- 세션 서버
  게스트 2 ------ 목록·입장 TCP -------- 세션 서버

  승인 정보를 받은 각 게스트는 위 세션 TCP를 종료한다.
  이후 각 게스트가 호스트와 별도의 게임 연결을 만든다.

  게스트 1 ===== 게임 TCP + UDP ===== 호스트
  게스트 2 ===== 게임 TCP + UDP ===== 호스트

게스트끼리는 직접 통신하지 않는다. 세션 서버도 게임 데이터를 중계하지
않는다. 호스트만 세션 관리 연결과 게임 연결을 동시에 유지한다.

프로세스별 주요 소켓

  세션 서버
    - sessionListenSocket: 새 TCP 연결을 받는 소켓 1개.
    - sessionPeerSocket: accept()가 반환한 연결별 통신 소켓.
      호스트와 게스트 연결마다 별도로 존재한다.

  호스트
    - sessionSocket: 세션 서버에 connect()한 TCP 소켓.
    - gameListenSocket: 게스트 게임 연결을 받는 TCP 소켓.
    - guestGameSocket: accept()로 얻은 게스트별 TCP 통신 소켓.
    - gameUdpSocket: 게스트들의 UDP 데이터그램을 받는 소켓.

  게스트
    - sessionSocket: 목록 조회·입장에 사용하고 종료하는 TCP 소켓.
    - gameSocket: 호스트에 새로 연결하는 게임 TCP 소켓.
    - gameUdpSocket: 호스트와 실시간 데이터를 주고받는 UDP 소켓.

함수 흐름

  TCP 접속을 받는 쪽
    socket(SOCK_STREAM) -> bind() -> listen() -> accept()
    -> 반환된 통신 소켓에서 send()/recv()

  TCP 접속을 요청하는 쪽
    socket(SOCK_STREAM) -> connect() -> send()/recv()

  호스트 게임 UDP
    socket(SOCK_DGRAM) -> bind(게임 UDP 포트) -> recvfrom()/sendto()

  게스트 게임 UDP
    socket(SOCK_DGRAM) -> bind(포트 0) -> sendto()/recvfrom()
    포트 0은 운영체제가 사용 가능한 임시 포트를 배정하게 한다.

accept()는 새로운 통신 소켓을 반환한다. 접속 대기용 소켓은 다음 연결을
계속 받아야 한다. UDP에는 listen()/accept()를 사용하지 않는다.
클라이언트 UDP의 명시적 bind()는 이 설계에서 로컬 포트를 분명하게
관리하기 위한 선택이며, 모든 UDP 송신에 반드시 필요한 절차라는 뜻은 아니다.

Windows에서는 프로세스 시작 시 WSAStartup(), 종료 시 각 소켓의
closesocket()과 마지막 WSACleanup()을 처리한다.

회의에서 정할 것
  - 소켓별 소유 모듈과 종료 책임자는 누구인가?
  - 블로킹 소켓+스레드, 논블로킹 방식 등 어떤 I/O 모델을 사용할 것인가?
  - 각 게스트 연결을 어떤 자료구조로 찾고 관리할 것인가?

======================================================================
3. Part A: 방 생성부터 게임 접속까지
======================================================================

정상 흐름
  1. 호스트가 게임 TCP·UDP 수신을 준비한다.
  2. 호스트가 세션 서버에 연결하고 SESSION_HELLO를 교환한다.
  3. ROOM_REGISTER로 방을 등록한다. 성공 후에만 공개 목록에 표시한다.
  4. 게스트가 세션 서버에 연결하고 SESSION_HELLO를 교환한다.
  5. SESSION_LIST_REQUEST/RESULT로 방 목록을 조회한다.
  6. 게스트가 JOIN_REQUEST를 보낸다.
  7. 세션 서버가 JOIN_OFFER를 호스트에게 전달한다.
  8. 호스트가 정원·입장 조건을 확인하고 자리를 예약한다.
  9. 호스트가 JOIN_DECISION을 보내고 세션 서버는 JOIN_RESULT로 중계한다.
 10. 게스트가 승인 응답 전체를 받고 세션 TCP를 닫는다.
 11. 새 게임 TCP 소켓을 만들고 호스트에 접속한다.
 12. GAME_HELLO에 입장 티켓을 넣어 인증한다.
 13. UDP 경로 확인과 초기 상태 적용을 진행한다.
 14. CLIENT_READY 확인 후 실제 조작을 허용한다.
 15. 호스트가 최신 참가 인원과 방 상태를 세션 서버에 보고한다.

입장 승인 시점에는 아직 게임 연결이 없을 수 있다. 따라서 세션 서버가
승인을 전달했다는 이유만으로 게스트를 플레이 가능한 상태로 표시하지 않는다.

세션 메시지 목록: 모두 TCP
각 요청에는 requestId를 넣고, 대응 응답은 같은 requestId를 사용한다.
아래는 후보 필드다. 자료형·필수 여부·최대 길이는 회의에서 확정한다.

  SESSION_HELLO / SESSION_HELLO_RESULT
    방향: 호스트·게스트 <-> 세션 서버
    목적: 버전 협의, 클라이언트 종류와 접속자 식별.
    요청: clientType, clientInstanceId, supportedProtocolVersions.
    응답: result, selectedVersion, clientId, errorCode.
    선택: 기존 접속 복구 증명.

  ROOM_REGISTER / ROOM_REGISTER_RESULT
    방향: 호스트 <-> 세션 서버
    요청: hostInstanceId, roomEpoch, roomName, maxPlayers,
          memberCount, reservedCount, phase, admissionPolicy,
          gameProtocolVersion, contentVersion, connectionDescriptor.
    응답: result, sessionId, 등록·복구에 사용할 증명, errorCode.
    선택: mapId, region. 연결 정보는 게임 TCP·UDP 주소/포트를 포함한다.

  ROOM_STATE_PUBLISH / ROOM_STATE_ACK
    방향: 호스트 <-> 세션 서버
    요청: sessionId, roomEpoch, stateRevision, 전체 방 메타데이터.
    응답: result, acceptedRevision, errorCode.
    탱크 위치나 체력 등 게임 상태는 보내지 않는다.

  SESSION_LIST_REQUEST / SESSION_LIST_RESULT
    방향: 게스트 <-> 세션 서버
    요청: pageSize, 지원 게임·콘텐츠 버전.
    선택: pageCursor, 검색 조건.
    응답: 공개 방 목록, nextCursor, result, errorCode.
    목록에는 티켓·복구용 비밀값을 넣지 않는다.

  JOIN_REQUEST / JOIN_RESULT
    방향: 게스트 <-> 세션 서버
    요청: sessionId, roomEpoch, guestId, 게임·콘텐츠 버전.
    선택: displayName, preferredRole.
    승인 응답: joinId, joinTicket, 유효기간, connectionDescriptor.
    거절 응답: errorCode. 표시 이름이나 희망 역할이 실제 권한은 아니다.

  JOIN_OFFER / JOIN_DECISION
    방향: 세션 서버 <-> 호스트
    심사 요청: sessionId, roomEpoch, joinId, 최소 게스트 정보,
               심사 제한 시간, 게임·콘텐츠 버전.
    심사 결과: joinId, approved, errorCode.
    승인 시: 예약 정보, joinTicket, 연결 정보.
    세션 서버는 joinId로 게스트 요청과 호스트 응답을 연결한다.

  JOIN_CANCEL / JOIN_CANCEL_RESULT
    방향: 게스트 -> 세션 서버 -> 호스트, 결과는 역방향.
    요청: sessionId, roomEpoch, joinId, 취소 권한을 확인할 정보.
    선택: reason.
    응답: 취소됨, 이미 만료됨, 이미 참가함, 권한 없음 등.
    취소는 미완료 예약만 해제한다. 이미 참가한 사람을 퇴장시키지 않는다.

  ROOM_RESUME / ROOM_RESUME_RESULT
    방향: 호스트 <-> 세션 서버
    요청: sessionId, roomEpoch, hostInstanceId, 복구 증명,
          최신 전체 방 상태와 필요한 미완료 입장 정보.
    응답: 복구 결과, 반영된 상태 버전, errorCode.

  ROOM_CLOSE / ROOM_CLOSE_RESULT
    방향: 호스트 <-> 세션 서버
    요청: sessionId, roomEpoch, stateRevision, reason.
    응답: 처리 결과. 이미 닫힌 방에 대한 중복 요청도 일관되게 처리한다.

  PING / PONG
    방향: 연결된 양쪽
    필드: pingId, 필요 시 송신 시각.
    목적: 연결의 응답 가능 여부와 왕복 지연 확인.

주요 오류 코드 후보
  VERSION_MISMATCH, INVALID_MESSAGE, UNAUTHORIZED,
  SESSION_NOT_FOUND, ROOM_FULL, ROOM_NOT_JOINABLE,
  HOST_TIMEOUT, HOST_DISCONNECTED, RESERVATION_EXPIRED,
  TICKET_INVALID, ALREADY_JOINED, INTERNAL_ERROR.

오류 코드의 정수 값, 재시도 가능 여부, 사용자 안내 문구는 별도로 정한다.
오류 응답만 보내는지 연결까지 닫는지도 오류별로 구분해야 한다.

4. 정원·예약·식별자·상태 일관성
======================================================================

정원 검사 기본안
  memberCount + reservedCount < 3 이면 신규 예약을 만들 수 있다.

memberCount는 슬롯을 점유한 참가자 수다. 호스트, 초기화 중인 참가자,
복귀 유예로 자리를 유지하는 참가자도 포함한다.
reservedCount는 아직 게임 인증을 하지 않은 신규 참가자의 유효 예약 수다.
readyCount는 초기화 완료 등 조작 가능 조건을 만족한 인원으로 별도 관리한다.

마지막 한 자리에 A와 B가 동시에 입장을 요청했다고 가정한다.
정원 검사와 예약 생성을 분리하면 두 사람 모두 승인될 수 있다.
따라서 호스트가 검사와 예약 생성을 한 작업처럼 처리해야 한다.
단일 처리 큐나 잠금 등 실제 방법은 구현 환경에 맞게 정한다.

예약 상태 변화
  승인: reservedCount +1.
  게임 인증 성공: reservedCount -1, memberCount +1, 상태는 INITIALIZING.
  초기화 완료: ACTIVE로 변경. memberCount를 다시 증가시키지 않는다.
  예약 만료·취소: reservedCount -1.
  참가자 퇴장 또는 복귀 유예 만료: memberCount -1.

중요한 식별자 구분
  sessionId: 방 ID. 세션 서버가 등록 결과로 부여하는 방안을 제안한다.
  requestId: 한 요청의 재시도까지 묶는 ID. 요청자가 생성한다.
  joinId: 하나의 입장 심사·예약 ID. 세션 서버가 생성하는 방안을 제안한다.
  playerId: 실제 게임 참가자 ID. 호스트가 부여한다.
  roomEpoch: 실제 게임 인스턴스 세대. 단순 세션 TCP 재접속과 구분한다.
  stateRevision: 호스트가 같은 방 세대에서 증가시키는 방 상태 버전.

기본 처리 규칙
  - 같은 requestId의 재요청에는 기존 처리 결과를 반환한다.
  - 중복 요청 때문에 새 예약을 만들거나 예약 시간을 늘리지 않는다.
  - 같은 방 세대에서는 높은 stateRevision만 새 상태로 반영한다.
  - 실제 게임이 유지된 채 세션 TCP만 복구되면 roomEpoch를 유지한다.
  - 게임 인스턴스가 재시작되면 새 세대로 구분하고 옛 티켓을 무효화한다.
  - 세션 서버는 현재 인증된 호스트 제어 연결의 갱신만 받아들인다.

게스트의 세션 TCP 종료는 정상 전환이므로 예약 취소가 아니다.
취소와 게임 인증이 동시에 발생하면 호스트의 처리 순서로 한 결과만 정한다.

회의에서 정할 것
  - ID의 크기·생성 주체·재사용 여부와 저장 범위.
  - 요청 결과를 얼마나 보관하고, 재시작 후에도 보관할지.
  - 요청 타임아웃 후 늦게 승인된 예약을 어떻게 취소할지.
  - 복귀 유예 참가자를 목록의 인원에 어떻게 표시할지.

======================================================================
5. Part B: 게임 연결과 한 틱의 처리
======================================================================

게임 연결 기본안
  GAME_HELLO
    -> GAME_ACCEPT 또는 GAME_REJECT
    -> UDP_BIND / UDP_BIND_ACK로 경로 확인
    -> INITIAL_STATE 수신·적용
    -> CLIENT_READY / CLIENT_READY_RESULT
    -> 실제 게임 입력 허용

UDP 바인딩은 게임 TCP 참가자와 UDP 송신 주소를 연결하는 절차다.
TCP에서 받은 연결 ID·연결 세대·바인딩 증명을 사용한다.
UDP에 적힌 playerId나 송신 주소만으로 참가자를 신뢰하지 않는다.
UDP 경로 확인의 challenge/응답 방식과 만료 조건은 회의에서 확정한다.

한 틱(tick)은 호스트가 게임 상태를 한 번 갱신하는 논리적 시간 단위다.
예를 들어 60Hz이면 초당 60번 연산한다. 렌더링 프레임과 전송 주기는
이 연산 주기와 같을 필요가 없다.

한 틱의 처리 순서 제안
  1. 수신 큐에서 처리 가능한 메시지를 가져온다.
  2. 연결 상태·역할 변경 등 제어 명령을 적용한다.
  3. 입력의 순서·역할·범위를 검사한다.
  4. 주행과 조준을 계산한다.
  5. 발사·장전·물체 상호작용을 처리한다.
  6. 물리·충돌·피해를 계산한다.
  7. 최종 상태와 변경 순서를 확정한다.
  8. 전송 주기에 해당하면 결과와 상태를 보낸다.

호스트 자신의 입력도 같은 검증과 연산 경로를 사용한다.
수신 스레드는 메시지를 큐에 넣고 게임 연산부에서 적용하는 방식을 제안한다.
Unity를 사용한다면 수신 스레드에서 Unity 오브젝트를 직접 변경하지 않는다.

회의에서 정할 것
  - 같은 틱의 역할 변경과 발사는 어떤 순서로 처리하는가?
  - 발사 시 사용할 포구 위치는 이동·조준 계산 전후 중 어느 시점인가?
  - 고정 게임 틱과 물리 업데이트를 어떻게 연결하는가?
  - 한 틱에서 처리할 메시지 수와 큐 최대 길이는 얼마인가?

======================================================================
6. 게임 메시지와 공유 상태
======================================================================

아래 필드는 후보이며 타입·필수 여부·범위는 패킷 명세에서 확정한다.
연결 정보로 확인 가능한 playerId를 매 요청에 중복해서 넣을지는 검토한다.

[TCP 제어 메시지]

  GAME_HELLO / GAME_ACCEPT / GAME_REJECT
    방향: 게스트 <-> 호스트.
    요청: sessionId, roomEpoch, gameProtocolVersion, contentVersion,
          joinTicket 또는 resumeTicket.
    승인: playerId, connectionId, connectionEpoch, UDP 바인딩 정보,
          필요한 게임 기준 정보와 resumeTicket.
    거절: errorCode.
    최초 입장용 티켓과 재접속용 티켓의 용도는 구분한다.

  INITIAL_STATE
    방향: 호스트 -> 게스트.
    필드: baselineId, serverTick, baselineReliableSeq,
          참가자·역할·경기 상태, 현재 객체 목록과 상태.
    분할 시: chunkIndex, chunkCount, 전체 크기 등.
    실행 파일·텍스처 등 게임 리소스 다운로드와 구분한다.

  CLIENT_READY / CLIENT_READY_RESULT
    방향: 게스트 <-> 호스트.
    요청: baselineId, 적용 완료한 reliableSeq, 초기화 결과.
    응답: 조작 허용 여부, errorCode.
    이 메시지는 대기실에서 사용자가 누르는 준비 버튼과 다르다.

  PLAYER_READY_REQUEST / PLAYER_READY_RESULT
    방향: 게스트 <-> 호스트.
    필드: actionId, ready. 응답에는 결과·확정 준비 상태를 넣는다.
    목적: 대기실의 준비 상태 변경.

  ROLE_REQUEST / ROLE_RESULT
    방향: 게스트 <-> 호스트.
    요청: actionId, 희망 좌석·역할, 현재 roleVersion.
    응답: 결과, 확정 역할, 새 roleVersion, 적용 serverTick.
    희망 역할을 보냈다는 이유로 권한이 즉시 생기지 않는다.

  ACTION_REQUEST / ACTION_RESULT
    방향: 게스트 <-> 호스트.
    요청: actionId, actionType, roleVersion, 필요한 매개변수.
    선택: 대상 entityId·generation, 예상 대상 상태 버전.
    응답: actionId, result, errorCode, 적용 serverTick, 결과 상태 버전.
    actionType 예: FIRE, RELOAD, GRAB, DROP.
    서로 다른 actionType마다 필수 데이터가 다를 수 있다.

  STATE_CHANGE
    방향: 호스트 -> 게스트.
    필드: reliableSeq, 적용 serverTick, 변경 종류, 확정 상태.
    목적: 역할·경기 단계 등 중요한 상태 변경을 전달한다.

  OBJECT_SPAWN / OBJECT_DESPAWN
    방향: 호스트 -> 게스트.
    생성: reliableSeq, serverTick, entityId, generation, 객체 종류,
          초기 위치·회전과 필요한 생성 상태.
    제거: reliableSeq, serverTick, entityId, generation, reason.

  RESYNC_REQUEST
    방향: 게스트 -> 호스트.
    필드: 마지막 적용 상태·순서, reason.
    처리: 호스트가 새로운 INITIAL_STATE를 전달하는 방식을 제안한다.

  LEAVE_REQUEST / LEAVE_RESULT
    방향: 게스트 <-> 호스트.
    필드: 요청 ID, reason, 처리 결과.
    처리: 참가 슬롯, 역할, 점유 물체, 관련 연결을 정리한다.

[UDP 실시간 메시지]

  UDP_BIND / UDP_BIND_ACK
    방향: 양방향.
    필드: connectionId, connectionEpoch, 바인딩 증명과 확인값.
    처리: 해당 TCP 참가자의 UDP 경로를 확인한다.

  INPUT_FRAME
    방향: 게스트 -> 호스트.
    필드: inputSeq, sampleTick, roleVersion, 주행·조준 입력.
    선택: 최근 입력 이력.
    오래된 입력은 버리고, 오래 끊기면 중립·제동으로 전환한다.

  VR_POSE_FRAME
    방향: 게스트 -> 호스트.
    필드: poseSeq, sampleTick, anchorId, anchorVersion,
          머리·왼손·오른손의 위치와 회전, 추적 유효 플래그.
    선택: 최소 손동작.

  WORLD_SNAPSHOT
    방향: 호스트 -> 게스트.
    필드: snapshotSeq, serverTick, requiredReliableSeq,
          객체별 ID·세대와 현재 상태.
    선택: 해당 클라이언트의 마지막 처리 inputSeq.
    첫 버전은 다른 스냅샷을 기준으로 하는 차분 압축 없이 시작할 것을 제안한다.
    여러 패킷이 필요하면 객체별로 독립 처리 가능한 묶음으로 나눈다.

  PING / PONG
    방향: 양방향.
    필드: pingId, 송신 시각 등. 지연·손실 측정에 활용한다.

[연출 메시지]

  GAME_EVENT
    방향: 호스트 -> 게스트.
    필드: eventId, serverTick, eventType.
    선택: 관련 객체, 위치.
    소리·불꽃처럼 생략 가능한 효과는 UDP 후보이고, 필수 이벤트는 TCP 후보다.
    체력·탄약·파괴 여부를 이 메시지 하나에만 의존하여 관리하지 않는다.

공유할 상태와 결정 주체
  - 호스트 확정: 역할·좌석, 탱크 위치·속도·체력, 포탑·포신 각도,
    탄종·보관 탄약·약실·장전 단계, 물체 점유, 포탄·적·경기 상태.
  - 클라이언트 측정 후 호스트 검증·배포: 머리·양손 추적값.
  - 로컬 처리: 자신의 최종 HMD 화면, 메뉴, 상태로 계산할 UI,
    피격 정보에 따라 실행하는 햅틱 효과.

TCP와 UDP에 같은 필드를 중복 전송하면 오래된 값이 새 값을 덮어쓸 수 있다.
처음에는 TCP의 확정된 이산 상태와 UDP의 위치·자세를 구분할 것을 제안한다.
중복 전송이 필요한 필드는 serverTick·상태 버전 비교 규칙을 함께 정한다.

======================================================================
7. 순서 보장·중복 실행·VR 좌표에서 주의할 점
======================================================================

7-1. TCP 신뢰성과 행동 실행 결과는 다르다
TCP가 바이트를 전달해도 연결이 끊기면 요청자가 실행 결과를 모를 수 있다.
예를 들어 발사는 성공했지만 ACTION_RESULT를 받기 전에 연결이 끊길 수 있다.
같은 actionId로 재요청하면 다시 발사하지 않고 저장한 결과를 반환한다.
이 결과를 언제까지 보관하고 재접속 후에도 유지할지 정해야 한다.

발사·장전은 TCP의 ACTION_REQUEST 경로에서만 실행하는 것이 기본안이다.
UDP 입력에도 발사 비트가 있다는 이유로 별도로 다시 실행해서는 안 된다.

7-2. TCP와 UDP 사이에는 공통 도착 순서가 없다
OBJECT_SPAWN보다 해당 객체의 WORLD_SNAPSHOT이 먼저 도착할 수 있다.
초기 상태 전송 중에도 새로운 게임 상태가 만들어질 수 있다.

기본안
  - 특정 serverTick의 일관된 INITIAL_STATE를 만들고 기준 순서를 포함한다.
  - 그 이후의 필수 변경은 이어지는 TCP 순서로 전달한다.
  - 초기 상태 적용 완료 확인 전에는 실제 조작을 허용하지 않는다.
  - UDP의 requiredReliableSeq까지 TCP 변경을 적용한 경우에만 반영한다.
  - 필요한 변경을 아직 못 받았다면 최신 상태만 제한적으로 대기시킨다.
  - 계속 해결되지 않으면 RESYNC_REQUEST를 보낸다.

순서 번호의 순환, 대기 시간·개수, 초기 상태 생성 중 변경 보관,
재동기화 중 입력 허용 여부는 LLD에서 구체화한다.

7-3. 역할과 객체의 과거 상태를 구분한다
roleVersion을 입력과 행동에 포함하고 현재 역할 버전과 비교한다.
역할 변경 전에 보낸 늦은 요청은 거절한다.
객체는 entityId와 generation으로 구분하는 방식을 제안한다.
첫 버전에서 경기 중 ID를 재사용하지 않는 방법도 검토할 수 있다.
connectionEpoch는 재접속 전 패킷을 구분하며 roomEpoch와 용도가 다르다.

7-4. VR 좌표 기준을 일치시킨다
기본안: 탱크 월드 좌표 -> 좌석·플레이어 기준 공간 -> 머리·양손 상대 좌표.
정할 항목: 단위, 축 방향, quaternion 성분 순서, 손 기준점,
탑승·하차·recenter 시 anchorVersion 변경, 추적 중단 처리.
로컬 HMD는 서버 응답을 기다리지 않고 최신 하드웨어 추적으로 표시한다.
원격 자세는 수신 상태 사이를 보간한다.
보간은 두 상태 사이의 중간값을 계산하여 움직임을 부드럽게 표현하는 것이다.

7-5. TCP 송신 큐가 중요 요청을 막지 않게 한다
위치·자세를 매 프레임 게임 TCP에 넣거나 큰 리소스 파일을 섞지 않는다.
이미 TCP에 들어간 바이트의 순서를 응용 프로그램이 바꿀 수는 없다.
따라서 전송량, 큐 상한, 큰 초기 상태의 분할 크기를 정해야 한다.

======================================================================
8. 공통 패킷 형식과 송수신 구현 계약
======================================================================

TCP 헤더 기본안: 총 28바이트
  magic              2바이트  프로토콜 식별
  protocolVersion    2바이트  프로토콜 버전
  messageType        2바이트  메시지 종류
  flags              2바이트  확장용, 초기에는 0
  payloadLength      4바이트  본문의 바이트 수
  requestId         16바이트  요청·응답 식별, 통지는 0

이 배치는 아직 확정 명세가 아니다. 세션·게임 채널별 메시지 번호 범위,
필드 자료형, 버전 호환 규칙을 회의에서 결정한다.

TCP 수신 처리
  1. recv()로 받은 바이트를 연결별 수신 버퍼에 추가한다.
  2. 헤더가 충분한지 확인한다.
  3. 헤더와 길이가 유효한지 검사한다.
  4. 본문 전체가 없으면 다음 수신을 기다린다.
  5. 완성된 메시지를 꺼내 처리한다.
  6. 버퍼에 남은 다음 메시지도 반복해서 확인한다.

한 번의 send()와 한 번의 recv()가 한 메시지에 대응한다고 가정하지 않는다.
send()도 일부만 전송할 수 있으므로 남은 바이트와 송신 진행 위치를 관리한다.
논블로킹 사용 시 '지금 처리 불가'와 실제 오류를 구분해야 한다.
TCP recv()의 0 반환은 정상 종료 의미다. UDP의 길이 0 데이터그램과 혼동하지 않는다.

데이터 표현 기본안
  - 고정 크기 정수와 네트워크 바이트 순서를 사용한다.
  - 문자열은 UTF-8이며 길이는 글자 수가 아닌 바이트 수로 검사한다.
  - TCP 본문은 JSON, 실시간 UDP는 명시적인 이진 형식을 제안한다.
  - 구조체 메모리를 그대로 전송하지 않는다. 패딩·포인터·표현 차이가 있다.
  - float 표현, 위치 단위, 회전 표현과 NaN·무한대 거부 규칙을 정한다.
  - JSON에서 64비트 값을 쓰면 사용하는 파서의 정수 정밀도를 확인한다.

초기 크기 제한 제안
  TCP 본문: 메시지당 최대 64KiB. 큰 초기 상태는 분할하고 전체 크기도 제한.
  UDP: 응용 헤더와 인증 정보까지 포함해 데이터그램당 1,200바이트 이하 목표.
  방 이름: UTF-8 최대 96바이트.

UDP는 자체 메시지 경계가 있으므로 데이터그램 단위로 해석한다.
각 데이터그램에는 버전, 종류, 방·연결 세대, 순서 번호, 샘플 틱,
본문 길이와 인증에 필요한 정보를 정의한다.
잘리거나 길이가 잘못된 데이터그램은 정상 메시지로 처리하지 않는다.

회의에서 정할 것
  - 각 필드의 정확한 자료형·범위·단위·최대 개수.
  - 알 수 없는 메시지·버전·오류 데이터의 처리와 연결 종료 조건.
  - 직렬화 함수와 소켓 송수신 함수 사이의 인터페이스.
  - 패킷 예제와 정상·잘못된 바이트 배열 테스트 데이터.

9. 타임아웃·연결 종료·보안 기본안
======================================================================

아래 수치는 구현 시작을 위한 제안값이며 성능 보장이 아니다.
  - 일반 세션 요청: 5초.
  - 호스트 입장 심사: 5초, 전체 입장 대기: 8초.
  - 신규 입장 예약: 30초.
  - 초기 상태 적용: 30초.
  - 세션 생존 확인: 5초 간격, 15초 무응답 시 비활성화.
  - 게임 생존 확인: 1초 간격, 5초 무응답 시 단절 판정.
  - 게스트 재접속 유예: 30초.
  - 주행 입력 유효기간: 마지막 정상 입력 후 약 100ms.
  - 게임 연산: 60Hz, 입력·자세: 30Hz, 상태 전송: 20~30Hz.

상황별 처리
  세션 서버 무응답:
    신규 공개 입장을 중단한다. 기존 게임 연결과 연산은 유지할 수 있다.
  호스트의 세션 TCP 단절:
    목록의 입장 가능 상태를 막고 복구 후 전체 상태를 다시 보고한다.
    이미 발급된 유효 티켓의 처리 정책도 명시해야 한다.
  승인 후 미접속:
    예약 만료 또는 명시적 취소로 슬롯을 돌려준다.
  게스트 게임 단절:
    입력을 안전 상태로 바꾸고 잡은 물체·역할·복귀 자리를 처리한다.
  호스트 게임 종료:
    최초 버전에서는 경기 종료 후 목록 화면으로 이동한다.
  게임 중 게스트 이탈:
    3인 필수라는 가정에서는 일시정지와 복귀 유예를 제안한다.
    유예 실패 후 경기 중단·대기실 복귀 여부는 게임 규칙으로 확정한다.

보안·검증
  - 목록의 공개 정보와 입장·복구용 비밀값을 분리한다.
  - 방 갱신·종료 권한은 인증된 호스트 연결과 연결한다.
  - 티켓은 방·예약·유효기간에 연결하고 재사용을 관리한다.
  - UDP 연결 확인용 난수만으로 공개망 보안이 완성되지는 않는다.
  - 공개망 TCP의 TLS, UDP 패킷 인증·재전송 공격 방지와 필요 시 암호화를 정한다.
  - 검증된 보안 라이브러리를 사용한다.
  - 손실·혼잡이 커지면 UDP 전송량을 줄이고 오래된 상태를 계속 쌓지 않는다.
  - 호스트는 역할·거리·속도·탄약·발사 간격·물체 점유를 검증한다.
  - 호스트 플레이어가 최종 권한을 가진다는 신뢰 전제는 남는다.

아래 이름은 설명용이며 확정 API가 아니다.

SessionServer
  방 등록·조회, 호스트 연결, 입장 중계, 요청 결과 관리.

        PublishRoomState, DisconnectSession.

AdmissionManager [호스트]

  후보: TryReserveSeat, ValidateJoinTicket, CommitAdmission,
        CancelReservation, ExpireReservations.

GameHost / PlayerConnectionManager
  게임 접속, 게스트 연결, UDP 경로, 초기화, 단절과 복귀.
  후보: AcceptGameConnection, BindUdpEndpoint, SendInitialState,
        MarkClientReady, DisconnectPlayer, ResumePlayer.

GameClient
  게임 연결, 입력 송신, 초기 상태 적용, 원격 상태 보간.
  후보: ConnectGame, SendInput, SendAction, ApplyInitialState,
        ApplyReliableChange, ReceiveSnapshot, RequestResync.

InputValidator / RoleManager
  플레이어 역할·버전·입력 범위와 행동 권한 검사.
  후보: ValidateInput, ValidateRole, ChangeRole, ValidateAction.

TankSimulation / WeaponSimulation / InteractionManager
  이동·조준·장전·발사·피해·물체 점유의 게임 규칙 적용.
  후보: StepTank, UpdateAim, TryFire, TryReload, TryGrab, ApplyDamage.

StateReplicator
  전체 초기 상태, TCP 상태 변경, UDP 스냅샷 생성·배포.
  후보: BuildInitialState, RecordReliableChange, BuildSnapshot.

ProtocolCodec / SocketTransport
  메시지 직렬화·역직렬화, 길이 검사, 실제 송수신과 연결 종료.
  후보: EncodeMessage, TryDecodeMessage, QueueSend, ReadSocket.
  메시지 해석과 게임 규칙 적용을 같은 함수에 몰아넣지 않는다.

12. 최소 검증 시나리오와 구현 순서
======================================================================

세션·접속 검증
  1. 호스트 등록 후 두 게스트가 목록 조회·입장·게임 연결에 성공한다.
  2. 마지막 한 자리에 동시 요청을 보내도 한 명만 예약된다.
  3. 같은 JOIN_REQUEST를 반복해도 예약 수가 늘지 않는다.
  4. 승인 응답을 못 받은 게스트가 같은 요청 ID로 결과를 확인한다.
  5. 승인 후 접속하지 않으면 예약이 만료된다.
  6. 예약 만료·취소와 게임 인증이 겹쳐도 인원을 중복 계산하지 않는다.
  7. 오래된 목록에서 입장하거나 입장 중 방이 닫혀도 올바른 오류를 받는다.
  8. 세션 TCP만 끊고 복구하면 기존 게임은 유지되고 목록이 복구된다.

게임 검증
  9. 호스트와 게스트 2명의 역할별 입력이 하나의 탱크에 적용된다.
 10. 같은 발사 actionId를 반복해도 포탄·탄약 차감은 한 번만 발생한다.
 11. 역할 변경 전의 늦은 입력은 적용되지 않는다.
 12. 초기 상태보다 UDP가 먼저 와도 존재하지 않는 객체를 잘못 만들지 않는다.
 13. 객체 제거 뒤 옛 스냅샷이 와도 객체가 다시 생기지 않는다.
 14. 두 사람이 같은 물체를 동시에 잡아도 최종 점유자는 한 명이다.
 15. 입력·추적이 끊겨도 탱크가 계속 전진하거나 같은 행동을 반복하지 않는다.
 16. 게스트 재접속 시 새 연결 세대로 구분하고 현재 상태를 복구한다.
 17. 호스트 종료 시 게스트가 명확한 종료 상태로 이동한다.

패킷·성능 검증
 18. TCP 헤더·본문을 나눠 보내거나 여러 메시지를 붙여 보내도 처리한다.
 19. 부분 송신·잘못된 길이·잘못된 자료형·초과 크기를 처리한다.
 20. 지연·손실·순서 역전 상황에서 상태가 회복된다.
 21. 호스트의 프레임 시간, 입력 지연, 초당 송수신량, 큐 길이를 측정한다.

각 테스트는 예상 응답 코드, 최종 memberCount·reservedCount,
남아야 하는 연결, 게임 상태를 기록한다.
로그에는 sessionId, roomEpoch, connectionId, serverTick,
requestId 또는 actionId, 메시지 종류, 결과·실패 사유를 남길 것을 제안한다.
티켓과 비밀키 원문은 로그에 남기지 않는다.

구현 순서 제안
  공통 프레이밍 -> 방 등록·목록 -> 입장 심사·예약
  -> 새 게임 연결·인증 -> UDP 바인딩·초기 상태
  -> 역할별 주행·조준·VR 표현 -> 발사·장전·물체 상호작용
  -> 단절·복귀·재동기화 -> 손실·부하 시험과 주기 조정.
